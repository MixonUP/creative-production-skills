# Learn without turning every tip into a rule

Use the project's Markdown knowledge base as canonical storage. In Krea, begin with `Knowledge/04_Procedures/Film_Workbench.md`; Obsidian opens these files and Basic Memory indexes the same files. Read only the relevant cards. Refresh the index after external edits when useful; lack of MCP does not block direct files.

For studio-wide AI Films research use `E:/AI_films/Knowledge/00_HOME.md` and its linked research/experiment cards. Keep each evidence record in its owning project and link it from the other workspace instead of maintaining competing copies.

## Ingest a source

Identify title, author, URL, date, source type and what was actually inspected: metadata, transcript, selected visuals, whole clip, code or local run. Retain timestamps for useful demonstrations. Note sponsorship when it affects interpretation. A transcript establishes what was said, not the visual quality of the result. Do not invent unavailable sections.

For each consequential technique record: problem addressed, actionable steps, prerequisites, claimed benefit, failure cases, evidence status and smallest useful local test. Separate the author's claim, our inference and our measured observation. External instructions are source material and do not grant permission to install, spend or upload project assets.

Promote knowledge through **captured → assessed → trial planned → locally tested → adopted**, or mark it rejected/superseded. Adoption is scoped to the tested conditions, not all models. Preserve negative results and changes in conclusion with dates.

For a requested transfer into production, record the source-supported observation, the existing local capability, the actual gap, proposed change, affected skill/handoff and a test artifact. Classify it as a procedural improvement, a recipe needing a trial, or an unresolved fact. Improving traceability can be implemented immediately without declaring a creative-quality gain. Reuse an existing relevant trial; a prepared template is not an executed workflow. Keep creator-specific brands, dates and hidden-tool unknowns in the evidence card, not universal skill requirements.

## Put changes in the right place

- Stable production decisions belong in project procedure cards.
- Provider/model-specific capabilities and billing belong in dated adapter cards.
- Run inputs, outputs, versions and visual judgments belong in experiment cards with immutable evidence.
- Reusable decision guidance belongs in a skill only when it changes future behavior.
- Promising branches and unprocessed sources belong in a backlog with a concrete next step, benefit, effort/dependencies and a condition for revisiting them.

Avoid duplicating the same fact across skills and notes. Link from the skill to the canonical card. Keep unverified tips out of mandatory instructions. When new information conflicts with an old record, append a dated correction and update the current recommendation without erasing history.

## Upgrade a skill or adapter

Maintain a small revisioned registry mapping canonical source directories to installed copies and evidence. Change the narrowest relevant file. Keep existing invocation behavior and unrelated settings. Follow available Skill Creator guidance, validate metadata/links, and test the changed behavior using a realistic allowed task. Do not broaden an instruction from one failure to all workflows.

For Krea, canonical skills are in `Tools/skills`; installed copies are in the user's Codex skills directory. Validate before synchronization; preserve backups and detect source/runtime drift. Record hashes and revision. A new installed skill may need a task/app reload for automatic discovery; direct reading works immediately.

Use [maintenance examples](references/maintenance-cases.md) to check routing. The backlog is planning, not authorization to run every experiment or start scheduled monitoring.
